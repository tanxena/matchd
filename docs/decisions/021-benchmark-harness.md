# 021 — The benchmark harness: what is measured, how, and when a run doesn't count

- **Status:** accepted (milestone 9). Chosen with the user:
  - benchmarks run on **AC power under the High performance plan**, stated in the hardware line with "nothing else running". One extra row, the resting mix under the **Balanced** plan, shows what a reader on a laptop with default settings would see; the clock-overhead row runs under both;
  - **the user runs `make bench-full` and `make bench-balanced`.** The harness was walked through first (the learning doc, §2), and `make bench-smoke` checks it in about a minute and a half;
  - the engine is pinned to logical CPUs 0–3 and the load generator to 4–7, with the claim about physical cores made **only because the sibling mapping was verified** (below);
  - **Windows-only numbers.** Linux is cross-compiled, and its tests are to run in CI, which hasn't run yet (review F-010);
  - core-latency quantiles come from a **finer, log-linear histogram** (amending decision 017), served at `GET /debug/latency`;
  - processes are pinned with **`SetProcessAffinityMask`**, the mask `start /affinity` sets, rather than by running `start` itself.
- **Code:** `bench/` (`loadgen`, `clockprobe`, `benchrun`, `report`, `internal/load`, `internal/result`, `internal/sysinfo`), `internal/metrics/loghist.go`, `internal/server/http.go` (`handleLatency`), `Makefile` (`bench-*`)

## Context

PRD 7 sets the rules:
- two latencies, matching-core (in-process) and end-to-end (over loopback), each as p50/p99/p99.9/max with the count;
- throughput, with the engine's and load generator's CPU;
- a separate, pinned load generator;
- ≥ 30 s warmup and ≥ 60 s measured;
- ≥ 5 interleaved runs per configuration, reported as median and min–max;
- three fsync policies, three order mixes, and a snapshot on/off pair;
- raw JSON per run, and README tables generated by a committed script.

## Decision 1: four programs, one process each

| program | does |
|---|---|
| `bench/loadgen` | the load generator: connects, drives the engine for warmup + window, writes what it measured as JSON |
| `bench/clockprobe` | the clock-overhead row: back-to-back reads of `internal/clock` |
| `bench/benchrun` | the interleaving script: runs a suite's runs in order, a fresh engine each time, pinned, and writes one result file per run |
| `bench/report` | reads the result files and generates the README's benchmark section |

The engine is the shipped `cmd/engine` binary, started with ordinary flags. Nothing about it is benchmark-specific except `GET /debug/latency`, which is always on (Decision 3).

**Why Go for the "script":** it needs process handles, affinity masks, CPU times, a console control event and JSON. That's a few system calls from Go, and a lot of fragile PowerShell. It is also testable (`plan_test.go` checks the interleaving).

## Decision 2: closed loop for throughput, open loop for latency

- **Closed loop** (`-rate 0`): each of 4 connections keeps 64 commands in flight. A free slot is filled at once, and every free slot is sent in **one write**. This finds **sustained throughput**: the rate at which answers come back when the engine is never waiting for work. End-to-end latency measured here is mostly queueing, about (in flight) ÷ (throughput) by Little's law, and is labelled as such. **Used for the fsync table**, where throughput is the question.
- **Open loop** (`-rate N`): commands are scheduled at N per second, spread evenly over the connections. One pacer goroutine spins on the clock and writes whatever is due. **Latency is measured from each command's *scheduled* time, not from when it was actually written**, so a load generator that falls behind can't hide the delay (no *coordinated omission*). How far behind it fell is recorded separately as **send lag**. **Used for the mix table, the snapshot row and the Balanced row**, where latency at a known load is the question.

**The rate: 20,000 commands/s.** In the smoke runs, closed-loop saturation on this machine was 50,000–68,000 commands/s, so 20,000 is well under it, about 30–40%. The engine is busy but not queueing. Both the rate and the window are flags, recorded in every result file.

**The pacer spins** rather than sleeps. A sleeping sender wakes late by the OS timer's granularity, and that lateness would land in the latency it measures. The cost is one busy CPU in the load generator, on its own cores, and that shows in its CPU column.

**Rejected:**
- *Closed loop for latency.* At saturation, latency is a function of the window you chose.
- *One run type for both.* A rate below saturation can't measure throughput.
- *Separate closed-loop throughput runs per mix in the main plan.* They'd add 15 runs (about 27 min). The suite exists (`benchrun -suite mix-throughput`) if wanted.

## Decision 3: where each number comes from

| number | source |
|---|---|
| matching-core latency (PRD 7.1a) | the engine's `GET /debug/latency`, read at the window's start and end and subtracted |
| end-to-end latency (PRD 7.1b) | the load generator: send (scheduled, in open loop) → receipt of the command's **first answer** (`Ack`, `Reject` or `CancelAck`), with `internal/clock` |
| throughput | closed loop: first answers received in the window ÷ window length. Open loop: commands *sent* in the window and answered ÷ window length. Counting answers received in the window would include a backlog sent before it, which could hide a sender that fell behind. That was found when a loaded test machine answered "6,466/s" for a 5,000/s schedule. The committed open-loop results are within 0.1% of the target either way. |
| engine counters | `/metrics` deltas: commands, trades, fsyncs and their mean, WAL bytes, snapshots, slow consumers |
| book size | `GET /instruments` order count at the window's start and end |
| CPU | the OS: engine and load-generator process times, every other process, interrupt/DPC time (Decision 7) |

**Amending decision 017: a log-linear histogram for the benchmark.** Decision 017 fixed the `/metrics` buckets (0.25, 0.5, 1, 2, 5 … µs) and said the benchmark would use them. From those, a table could only say "p50 between 0.5 and 1 µs", and couldn't give a maximum at all. So the engine also records each command's span into a `metrics.LogHistogram`:
- 32 linear sub-buckets per power of two (the HDR histogram layout), so every bucket is narrower than 1/32 of the values in it;
- every quantile, and the maximum, is reported as its bucket's upper bound: **at most 3.125% above the true value, never below**;
- O(1) per observation (a bit length and two shifts), 12 ns, no allocation; 1,152 buckets, about 9 KB;
- **recorded after the span's closing clock read**, so it isn't part of what it measures;
- served as JSON at `GET /debug/latency`, not in `/metrics`. Decision 017's reasons for keeping `/metrics` small still hold.

It is **always on**, so the benchmarked binary is the shipped one.

**Rejected:** raw samples (exact, but about 50 MB per run held in the engine, and a benchmark mode the shipped binary doesn't have). Also rejected: the `/metrics` buckets alone, too coarse to report.

## Decision 4: the order mixes, and a book that holds its size

Prices sit on a fixed grid around a mid of 1,000,000 ticks, on one instrument with tick 1 and lot 1:
- **passive:** GTC limit 1–10 ticks from mid, on its own side, so it always rests;
- **crossing:** IOC limit 10 ticks *through* mid, so it trades against the other side best-first and never rests. IOC keeps the book one-sided by construction, and the mid never moves;
- **cancel:** one of the connection's own resting orders, chosen at random.

| mix (PRD 7.6) | passive | crossing | cancel |
|---|---|---|---|
| resting ("90% limit away from mid") | 90% | 10% | – |
| crossing ("50% at or through mid") | 50% | 50% | – |
| cancel-heavy ("40% cancels") | 50% | 10% | 40% |

**The book holds about 10,000 resting orders.** With balanced flows alone, the book's size is a random walk. Tuned to drift down instead, the book peaked at 80–870 orders in a simulation against the real book (the first version of `TestMixesHoldTheBookNearTarget`). A book that thin makes every operation cheap and flatters the numbers. So each crossing order's quantity is scaled by the book's size over a target (clamped to ¼–4×): smaller below the target, so the book fills; larger above it, so it drains. The test now measures, over 400,000 commands per mix against the real book:
- resting: 9,300–10,400 orders;
- crossing: 8,200–8,700;
- cancel-heavy: 6,200–7,000. Cancels alone nearly balance passive inflow there, so even the smallest crossing orders hold it under the target.

The count at each window's start and end is recorded.

**A guard:** a connection with 10,000 resting orders sends a cancel instead of a passive order ("cap cancel"). The depth control should make that never happen. More than 0.5% of commands marks the run disturbed.

## Decision 5: interleaving, repetitions, a fresh engine

- **Rounds.** `full` runs 5 rounds, and each round runs, in this order:
  1. the clock probe;
  2. `always`, `group:1ms`, `never`;
  3. `resting`, `crossing`, `cancel-heavy`;
  4. `snapshots-on`, `snapshots-off`.

  Each table's PRD 7.5 cycle holds, and the tables interleave with each other too, so slow drift (temperature, background activity) lands on every configuration alike. 45 runs, about 75 min.
- **`balanced`** runs separately, after switching plans: 5 × (clock, resting), about 10 min. A plan can't be switched in the middle of a suite. Its row is compared with the main suite's resting row, run at another time; the table says so.
- **Every run starts a fresh engine on an empty data directory** (deleted afterwards). No run inherits another's WAL, book or warm caches. Warmup reaches steady state on its own.
- **15 s cooldown** between load runs.
- **Seed 1 for every run,** so repetitions differ only in timing and the machine. What a cancel targets and how large a crossing order is depend on which orders are still resting, so streams aren't byte-identical.
- **Snapshots off** except in the snapshot row: one snapshot every 10 s there, as PRD 5.4 asks.

## Decision 6: pinning

- **The masks:** `0x0F` (logical CPUs 0–3) for the engine and `0xF0` (4–7) for the load generator. The clock probe runs on the engine's mask, because that's where the engine reads the clock.
- **Verified:** `GetLogicalProcessorInformation` on this i7-8650U reports cores {0,1}, {2,3}, {4,5} and {6,7}, so the engine has physical cores 0–1 and the load generator 2–3. **No physical core is shared. All four share the 8 MB L3 cache.** `benchrun` checks this before starting, and refuses masks that share a core. Every result file records the masks and the topology.
- **How:** `benchrun` starts each process and immediately calls `SetProcessAffinityMask`: the same per-process mask `start /affinity` sets, covering every thread, present and future. It then reads the mask back with `GetProcessAffinityMask` into the result file, and a mismatch marks the run disturbed. `start` itself wasn't used, because it doesn't return the started process's id, which the harness needs to read the engine's CPU time and to send it the CTRL_BREAK that shuts it down. Between creating the process and setting the mask, the process is only starting up, 30 s before measuring begins. Each row's equivalent `start /affinity` lines are listed in the README, for repeating a run by hand.
- **`GOMAXPROCS=4` for each process.** The Go runtime sizes `GOMAXPROCS` from the CPUs it can use **at startup**, before the mask is applied, so without this it would schedule 8 Ps onto 4 CPUs.

## Decision 7: when a run doesn't count

`result.Assess` judges every finished run, and `benchrun` writes the reasons into the file (`disturbed`). A disturbed run's numbers are **never** in the README: `report` refuses to run until there are none (`-allow-disturbed` leaves them out, with "4 of 5†" in the row and the list underneath). A failed run has no numbers at all.

Since review F-014, clock-probe runs get the other-processes check too, measured over the probe's own run. Before, they were checked only for power and pinning.

| check | limit | why |
|---|---|---|
| other processes' CPU, averaged over the window | 0.35 logical CPUs (~4% of the machine) | "nothing else running", measured. A quiet desktop still has the window manager, the kernel's System process and services. A browser playing media used 1–2 CPUs in the smoke runs, and the check named it |
| power | AC; plan, overlay and source unchanged from start to end | a plan change mid-run changes the CPU's clocking |
| affinity read back | equal to what was set | |
| measured window | within 2% of the requested 60 s | a longer window means the load generator was descheduled or the machine stalled |
| cap cancels | ≤ 0.5% of commands | the mix was distorted |
| open loop: send lag p99 | ≤ 100 µs | the load generator didn't keep its schedule |
| open loop: answered rate | ≥ 98% of the target | the rate wasn't sustained |
| slow-consumer disconnects | 0 | |

**Other processes are counted from the OS's process list** (`NtQuerySystemInformation`, as Task Manager does), not as machine busy time minus the engine and loadgen. The first version did the latter, and reported 1.7–2.2 "other" CPUs in closed-loop runs. Much of that was **interrupt and DPC time**: the loopback network stack carrying the benchmark's own traffic, which belongs to no process. It is now recorded separately (`interrupts`), and the five busiest other processes are named in each file.

**The suite itself refuses to start** (`-force` overrides and marks every run) if:
- the power source isn't AC, or the active plan's *personality* isn't the one the suite needs. Personality is the plan's kind, which survives renaming or duplicating it, so a restored "High performance" plan is recognised whatever its GUID. The mapping 0 = power saver, 1 = high performance, 2 = balanced was read from the three built-in plans on this machine (`TestPersonalities`);
- the ports are in use;
- under 5 GB is free for the data directories;
- the results directory already holds results, so a suite is never mixed with another.

## Decision 8: the files and the README

- **One JSON file per run** in `bench/results/<suite>/`, schema 1 (`bench/internal/result`), holding:
  - the exact argv of every process, the environment set, and the `start /affinity` equivalents;
  - masks requested and read back;
  - the machine (CPU, cores and their logical CPUs, caches, RAM, OS), Go version, git commit (marked `-dirty` if tracked files outside `bench/results` differ), and power before and after;
  - every measurement, including the full latency histograms, so new quantiles can be computed later without re-running;
  - the disturbance verdicts.
- **`bench/report`** generates the README's benchmark section between two markers. The hardware statement is stated once and comes from the files. So does "nothing else running" (the median and maximum other-process CPU actually measured), and the pinning claim (from the recorded topology). Every core-latency table carries the clock footnote (source and read cost, PRD 7.1 and decision 017). Cells are **median (min–max) across runs, never the best run**. Each row's exact commands are listed.

## Decision 9: Windows only

All tables are Windows 11 on this laptop. Linux is cross-compiled (`make ci`), and the suite is to run in CI for correctness only, which hasn't happened yet (review F-010); there are no Linux benchmark numbers, and the README doesn't promise any. `bench/internal/sysinfo` implements its OS calls for Windows only. Elsewhere they return `ErrUnsupported`, so the bench programs still build.

## Environment caveat: Microsoft Defender

This is an environment caveat, not a code change. Defender's real-time protection is on, and **it scans files in the benchmark's data directory when they're created, closed or renamed**, but not appends to an open file. Measured over 10 s each (`MsMpEng.exe` CPU):
- idle: 0.02 CPUs;
- appending and fsyncing one open file, as the WAL does: 0.02 CPUs;
- creating, closing and renaming 256 KB files, as snapshots and segment rolls do: 0.60 CPUs, with 0.14 still in the 10 s after.

That work runs during measured windows: snapshots in the snapshot row, a fresh data directory per run, and its deletion during the cooldown. It counts against "nothing else running", and may slow the disk the WAL fsyncs to. It wasn't established as the cause of the one 5 s fsync stall seen in a smoke run ([decision 022](022-slow-consumers-and-durability-stalls.md)).

`bench/CHECKLIST.md` step 1b excludes the data directory for the duration of the runs. That needs an administrator PowerShell, since exclusions can't even be read without one. Whether an exclusion was set must be stated in the README's environment line: the harness can't read it, so the user says so.

## Costs and limitations

- **Loopback TCP is not a network.** End-to-end latency includes two kernel network stacks on one machine and the L3 the two processes share. It's an upper bound on what the engine adds, not a network figure.
- **End-to-end latency includes the WAL fsync** (`group:1ms` in the latency tables). In the smoke runs the fsync itself averaged 1.4–2.4 ms on this laptop's SSD, which dominates end-to-end p50 (3–4 ms). That's what the durability contract costs here, and the fsync table shows it per policy.
- **Quantiles are up to 3.1% high** (Decision 3). The tables say so.
- **The window edges are scraped over HTTP.** The engine's counters cover a slightly wider window than the load generator's. *(Review F-018: in the committed results it was 100–220 commands per open-loop run wider, 5–18 ms of traffic, not about a millisecond as first written. A process-list query sat between the first scrape and the start of the window, and sending continued until after the second scrape. That is about 0.02% of samples, negligible for the quantiles, though a core-latency maximum could come from those edges. Runs from the fix on read CPU times before the first scrape and stop sending before the second, leaving one scrape at the start and the in-flight commands at the end.)*
- **The open-loop pacer always costs one busy CPU** in the load generator.
- **Synthetic mixes, one instrument, one machine.** The numbers describe this engine under this protocol, nothing more (PRD 7.7: no comparisons).

## Tests

- **`internal/metrics`:** buckets tile the line with no gaps and are ≤ 1/32 wide; quantiles are never low and at most 3.125% high on 200,000 log-uniform values; the mean is exact; snapshot arithmetic and JSON round-trip; no allocation; concurrent recording under `-race`. `/debug/latency` agrees with `/metrics` (`TestMetricsEndpoint`).
- **`bench/internal/load`:**
  - each mix's fractions, prices and quantities;
  - cap cancels and cancel targets;
  - the depth control against the real book;
  - out-of-order answers are errors;
  - open-loop latency is measured from the schedule;
  - closed- and open-loop runs of every mix against an in-process engine, checking every number the report uses.
- **`bench/internal/result`:** each disturbance rule on its own.
- **`bench/internal/sysinfo` (Windows):** the topology; affinity set and read back on a child process; CPU times; the process list's struct offsets checked against `GetProcessTimes`; power-plan personalities.
- **`bench/benchrun`:** the full plan interleaves each table's cycle, 5 runs each, round by round; smoke covers every configuration in under 5 minutes; command lines.
- **`bench/report`:** median and range; disturbed runs refused, or left out and listed, never counted; the hardware, pinning and footnote text; the README splice.
- **Planted bugs, all 11 caught:**
  - a histogram index off by one shift;
  - quantiles from the bucket's lower bound;
  - crossing orders at mid;
  - a cancel target left live;
  - open-loop latency measured from the write;
  - an out-of-order answer accepted;
  - the median taken as the best run;
  - disturbed runs counted;
  - snapshot runs not alternating;
  - other-process CPU never flagged;
  - the depth control disabled.
